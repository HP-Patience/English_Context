# 多用户数据库迁移与发布

多用户生产发布由 GitHub Actions 的 `master` 部署工作流执行。部署包包含迁移 SQL、管理员回填脚本与迁移运行器；服务器不构建、不安装依赖，也不需要把数据库凭据交给 GitHub Actions。

## 生产备份

迁移前确认 custom-format PostgreSQL 备份可由 `pg_restore --list` 读取，并在受控运维记录中保存备份路径和校验值；不要把生产存储路径或数据库凭据写入 Git。

## 自动部署顺序

部署脚本先解包 release，并把服务器现有环境文件安全链接到 release。随后在**仍由旧版本服务**时执行准备阶段：

1. 应用 `20261002_multi_user_accounts`，增加可空账号字段。
2. 从生产环境读取既有 `APP_AUTH_USERNAME` 和 `APP_AUTH_PASSWORD_HASH`，将 `local-user` 的现有学习数据回填为管理员。
3. 验证恰好一个 active admin，且所有用户都有账号凭据。
4. 应用 `20261002_multi_user_interactions`。

准备阶段成功后才切换 `current`、重启新版本并执行本机健康检查。新版本健康后，部署脚本才应用 `20261002_require_account_credentials`，将用户名和密码哈希改为必填。

迁移脚本通过 `psql` 在服务器执行；密码只作为子进程环境变量，不放在命令行、SQL 文件、日志或 GitHub secrets。每条迁移 SQL 与对应的 `_prisma_migrations` 记录在同一个事务里提交，并校验 Prisma migration SHA-256。已应用 migration 若校验和不一致，部署会失败关闭。

管理员回填是幂等的：如果管理员和所有凭据已经存在，重试部署不会重置管理员密码。

## 失败与回滚边界

- 准备阶段失败：新版本尚未切换；旧版本继续运行，新增的可空列或互动表不会要求旧版本读取。
- 新版本启动或健康检查失败：保留现有自动回滚流程；此时必填约束尚未应用，旧版本仍可工作。
- 最终必填约束失败：PostgreSQL 事务回滚，已健康的新版本继续运行；应用会校验并写入账号凭据，因此可在可空列状态继续服务，后续部署会重试约束迁移。日志会输出警告，不会回滚到不兼容的旧版本。
- 不要因为部署报错就删除表、改写 `_prisma_migrations` 或恢复备份覆盖新写入数据。数据库恢复前应先评估迁移阶段及新版本写入。
- 不使用 `prisma db push` 替代生产迁移。

## 约束

- 不在生产服务器构建、安装依赖或执行高内存任务。
- 不把生产环境文件、密码、数据库 URL 或 API Key 放入 Git、日志、命令参数或归档包。
- 当前 IP + HTTP 仅为临时熟人测试约束；公网正式使用前应配置 HTTPS。
